# Authorization and evidence profile v1-draft

**Status: adopted design draft, revision 2, not implemented or interoperability-qualified.** Profile identifier: `omworld.authorization-evidence.v1-draft`. This profile records the maintainer-approved consolidated design for #4/#6 and the bounded evidence decisions in #5. It is separate from legacy v0. Adoption of this document is not a freeze, community consensus, author endorsement, deployment, adapter, or scientific result. Issues #4–#6 remain open for implementation-independent design/conformance follow-up; #7/#8 remain open and deferred.

The [dependency and step-binding closure](authorization-evidence-dependency-closure.md) controls B1–B3 and supersedes earlier optional-consent and unspecified-mapping text. This is a draft-revision compatibility break; pin revision 2 and exact schema bytes.

## Scope, legacy and structural schema

[Structural JSON Schema](authorization-evidence-v1-draft.schema.md) defines 28 closed object types. It is prose/specification material under CC-BY-4.0, including its fenced machine-readable representation; it is not a runnable verifier. Its `$id` is an identifier, not a claim that a hosted schema endpoint exists. JSON Schema checks shape only: identity, signatures, hashes, containment, time, evidence availability and authorization need separate semantic verification. Critical ArtifactRef profiles must resolve to the closed dependency types and semantics in the closure document; unsupported or unavailable dependencies cannot verify.

Legacy Intent/Mandate/ExecutionProof objects and their formulas are unchanged. No old mandate is auto-upgraded, no historical consent/version is backfilled, and this profile does not reinterpret old payloads. Consumers must opt into the exact profile identifier; unsupported identifiers do not downgrade. A profile change requires a new explicit identifier. This draft is a bounded design, not a claim that all legacy open questions have been solved globally.

## Objects, canonical form and signatures

Each new object carries profile, object_type and id. New-object id is `sha256:` followed by 64 lowercase hexadecimal digits of SHA-256 over RFC8785 JCS of the object excluding id and signature. For signed types, signature input is SHA-256 over JCS of the object excluding signature, retaining id, profile and object_type. These are new-object definitions, not replacements for legacy formulas. All JCS values must satisfy RFC8785/I-JSON constraints; unsupported numeric precision or encodings fail structural/semantic acceptance. Monetary amounts use integer decimal strings, never floating-point conversions.

Signature carries scheme, key_ref and value. The dependency identity profile specifies exact signing scheme, digest interpretation, encoding, key format, domain and trusted identity/key-history/delegation rules; these cannot be inferred from a familiar scheme name. Unknown or missing suites mean unsupported/unavailable, not verified. Since the wrapper is excluded from payload id, a valid id alone says nothing about signer authority: independently validate the signature, actor/root binding and permitted suite. Accepting a different wrapper must never bypass that actor binding.

Ref contains id/object_type/profile and resolves to the exact new-object bytes. ArtifactRef contains SHA-256 digest and media_type and resolves to opaque evidence bytes. Recompute digest/id, validate requested object type and every applicable signature; a locator is an external convenience, not a trust root. Same ref with different bytes is inconsistent. Times are UTC RFC3339 ending Z and compared as instants; temporal intervals use `[valid_from, expires_at)`. Authorization objects require issued_at, expiry and signer-scoped nonce. issued_at precedes expiry; action/approval time must fall inside every applicable interval. Scope of nonce uniqueness is actor root + object_type + profile; replay tracking requires the declared single-deployment evidence/budget profile.

The schema uses closed objects (`additionalProperties: false`), with all listed keys required. Empty arrays explicitly express “none” only where allowed; they do not grant authority. External policy/profile artifacts remain dependencies: their missing or unsupported semantics prevent full verification, not an invented permissive default.

## Immutable principal authority and Agent acceptance — D01/D02

Principal signs immutable Intent. Agent separately signs Acceptance, referencing Intent, root/key/delegation path, Plan and exact DependencyManifest; principal-signed Intent is not modified to insert executor. Acceptance is the Agent's commitment and cannot enlarge Intent authority. Its content id is the mandate reference for this profile; legacy `mandate_id` is not silently repurposed.

Plan contains ordered action templates and inputs, not Invocation references containing acceptance_ref. This avoids the cycle Acceptance → Plan → Invocation → Acceptance. Each concrete Invocation references Acceptance and plan_index and must match its precommitted template (same tool/version, exact input digest, operation/resource/budget within the template). Changed plan or dependencies require a new Acceptance. Plan exists before acceptance signing; aggregate proof reveals the same plan through the export linkage.

Every EvidenceBundle requires exactly one principal-signed Consent bound to its exact Acceptance and DependencyManifest. It can only narrow the original Intent; expansion requires a new Intent. There is no skip-consent predicate. Restricted per-call approval remains independently required. See the closure document for exact ordering, identity and binding rules.

## Permission sources and action coverage — D03/D04

Adopt versioned registered baseline plus tightening-only deployment restrictions. Registry entries describe behavior/trust and are not principal consent or proof of truthful behavior. ToolEntry explicitly identifies provider and registrar; the registry/identity profile determines who is authorized to attest the registration. ToolEntry and DeploymentPolicy revisions are immutable. Semantic changes publish a new version, or a new tool_id when capability identity no longer remains stable. Mutable “current” discovery pointers never retarget accepted dependencies.

Action tuples identify tool_id+version, operation, explicit resource set, interval, asset/network and max_call_budget. No glob/regex, implicit wildcards or cross-asset conversion. Resource-less operations use the literal `not_applicable`, reserved as a marker, not a real resource identifier. Containment requires matching tool/version/operation and asset/network, resource-set inclusion, interval inclusion and no larger integer budget. Deny matches the same tuple dimensions and applies to actions within the deny interval and up to its declared budget; to deny all amounts the author must enumerate the applicable finite authorized ceiling. Ambiguous/unsupported deny semantics cannot be treated as verified authorization.

All effective authority sources must cover the concrete action, and no applicable deny may match. operation_class is a behavioral label, not a total order: admin and destructive are not compared by numeric max. Registered behavior must explain actual effects and composite operations; false “read” labels cannot hide transfers. Deployment may subtract actions or add conditions; inability to demonstrate non-expansion is not a compatible tightening. Changing operator/jurisdiction/trust is not ordinary endpoint rotation.

Delegation uses scope-covering rather than token-name membership; issuance structure and concrete-action checks are separate. A child may preserve operation/resource scope and shorten time, making whole authority strictly smaller. Fully equal authority is not strict narrowing. Other dimensional narrowing must use an explicitly supported identity/scope profile; unknown grammar is not accepted by guesswork. Multi-agent/sub-mandate execution is not established by operational-key delegation.

## Confirmation, keys and versions — D05–D09

For this new profile only: automatic omits an additional human confirmation layer but preserves every other constraint. human-in-loop requires principal affirmative approval of the exact Invocation after presentation. restricted requires explicit out-of-band principal approval and cannot be self-approved by an autonomous agent. This is a new-profile choice; legacy human-in-loop wording is not rewritten to assert it always meant affirmative approval.

InvocationApproval binds principal, Acceptance, Invocation and manifest, nonce, issued_at/expiry, mode and channel_evidence_ref. The closed ConfirmationProfile and ChannelReceipt definitions establish who approved, what bytes were presented, timing, permitted reuse/replay and genuine out-of-band provenance where required; merely putting `out_of_band` in a signed field is insufficient. Approval precedes action and does not transfer across changed invocation/context/version. Consent is not a substitute for this per-call check.

Treat Intent cancellation, credential expiry/revocation, normal key rotation, key compromise, tool suspension and service unavailability as distinct events with attributable effective times. Apply original proof key-history/timestamp requirements, including the compromise distinction. Neither cancelled Intent nor retired key alone defines every downstream historical result. Adversarial deployments cannot use the legacy single-trust-domain identity exception as an authorization bypass.

DependencyManifest pins registry snapshot, entries, deployment policies, identity, confirmation, custody, evidence, budget and relay profiles. Resolve at acceptance and again for action/verification against the same references; record changed events separately. Missing versions do not mean latest. Old mandates retain their historical rules and expiry; deprecation does not guarantee service. Deployment denial can block a call without rewriting the old record as never valid. New profile use requires explicit new objects and consent where needed.

Discovery reproducibility includes query, registry snapshot, deployment policy snapshot, filters and ranking-version inputs. Search/describe do not authorize; concrete-action check is separate. Hidden mutable policy cannot be omitted from a “same state” reproducibility claim.

## Budget and evidence closure — D10

Per-call max is not cumulative authority. Limits explicitly carry total_budget, with asset/network and integer amount; Acceptance fee_quote must fit principal's corresponding ceiling. A declared single-deployment budget/reservation profile must account for outstanding reservations and consumed amounts and define atomic reservation, release and audit provenance before full budget authorization can be established. Without such a supported profile, result is unable-to-determine, not “budget safe.” Cross-deployment concurrency and duplicate fulfillment are not supported here. No ledger implementation is delivered.

EvidenceBundle references Intent, Acceptance, optional Consents, approvals, manifest, ordered Invocations/contexts, complete aggregate proof bytes and exported evidence. It is an outer dependency closure, not a change to existing ExecutionProof signature/hash formulas. Its aggregate proof and Invocation/Context fields follow the exact revision-2 StepBinding bijection in the closure document; missing or mismatched correspondence cannot verify. No legacy verifier is claimed to support it. Validate the full aggregate; adjacent steps are local dispute evidence, not a complete proof. Excluding prev_hash from the existing step hash does not recursively commit all ancestry; aggregate signature and full traversal are separate checks.

Results are separated by layer: unsupported profile, unavailable dependency, invalid syntax/signature/identity, authorization unsatisfied, evidence mismatch, success criteria unsatisfied, or verified under declared assumptions. These are semantic categories, not a deployed error API. Missing evidence is not automatically fraud, slashable misconduct or verified performance. This profile does not silently change legacy slashing or settlement rules.

## Evidence decisions — E01–E07

- **Custody:** provider is the designated default custodian, expressly identified in signed CustodyProfile. Mirrors are optional; retention_until covers the dependency's declared challenge and appeal periods. Missing retention/window/access semantics prevents a full evidence claim. Provider identity and signed promise do not guarantee availability or truth; missing bytes means replay unavailable. No arbitrary retention duration or permanent service is promised.
- **Context:** ContextManifest pins pre-call state, retrieval procedure and provisioner-signed Configuration evidence, with provenance/time. Returned evidence remains linked by output_hash/aggregate. Pure input-determined functions may omit context; live state, session data and hidden config cannot be excused by HTTP/read labels. Stateful writes distinguish pre-state from output/post-state evidence. Exact context_hash bytes are SHA-256 digest of the resolved JCS ContextManifest bytes including its id; the step's own hash formula is unchanged. This new binding is not applied retrospectively to legacy context_hash.
- **Configuration:** use this manifest path for the new profile, rather than silently treating the old out-of-step lean as already resolved. Provisioner signature establishes attribution, not safety. Unavailable bytes cannot support deterministic replay. Retrieval evidence needs corpus, procedure/model/filter/scoring and output plus the relevant deterministic assumptions; equal corpus alone is insufficient.
- **Multi:** satisfy every required Intent evidence dimension with its specified suite/verifier/trust/freshness. External evidence does not replace Agent aggregate signature or principal consent. evidenceHash is not automatically output_hash; buyer key, publisher, payment and delivery remain separate claims.
- **Cross-chain:** only an explicitly pinned single trust-path relay profile is in scope. It must state source/destination chains, finality/freshness, exact-JCS-byte commitment, attributable relayer and trust/failure assumptions. Unsupported relay semantics prevents qualification. Heterogeneous-relayer paths and a new relay primitive are not supported. No bridge or adapter is implemented.
- **Parallel:** sequential ordered actions only. No Merkle composition, fan-out/join semantics or parallel proof is adopted. Do not manufacture a sequential label for a genuinely parallel dependency graph.
- **Privacy/outcomes:** private controller-owned sidecars hold deletable raw material; deletion evidence preserves claims/commitments, not reconstructible deleted bytes or proof of physical erasure/legal compliance. Subjective success criteria reference an attributable evaluator/process; its judgment is not independent objective truth. No default economic penalty follows automatically from a subjective judgment.
