# Authorization/evidence v1-draft — dependency and step-binding closure

**Design-draft revision 2.** This is the controlling clarification for B1–B3 in [the profile](authorization-evidence-v1-draft.md). It supersedes the earlier optional-Consent rule and unspecified dependency/mapping choices for this draft only. The [28-object structural schema](authorization-evidence-v1-draft.schema.md) is synchronized. No legacy field, hash or signature formula changes. This remains specification work, not a verifier, adapter, ledger implementation, conformance experiment or frozen release.

The draft identifier remains unchanged because no deployed/qualified consumer was established. Revision 1 payloads missing newly required consent/step bindings are not silently accepted: draft consumers must pin the exact schema/specification artifact digest and revision 2. Any future qualified release requires a new immutable published profile identifier. This is an explicit draft compatibility break, not backward compatibility with revision 1. Unknown dependencies fail as unsupported/unavailable rather than permissive defaults.

## B1 — principal consent is mandatory

Every EvidenceBundle contains **exactly one** principal-signed Consent. The same principal must sign Intent, Consent and every required InvocationApproval. Consent references the exact Acceptance and DependencyManifest and can only narrow Intent authority. It cannot alter Intent deny, budget, expiry or identity. Changes to Acceptance, plan or manifest require new Consent; no string/policy inference permits skipping it. Thus opaque evidence_requirements never substitute for principal authorization of trust/version choices. An enlarged scope requires a new Intent, not consent against a restrictive old one.

Compare principal/Acceptance/delegation/Consent limits on exact tool_id+version, operation, finite resource set, interval, asset/network and integer budgets. Every action must be covered by each applicable allow tuple and not match any applicable deny tuple. Per-call and total ceilings are separate. Whole child authority must be strictly narrower than parent: containment across every dimension, with at least one strict reduction. No wildcard/regex, numeric operation-class ordering, currency conversion or equal-authority delegation. Unsupported dimensions are not guessed. A deny tuple covers matching action/resource/time and amounts up to its finite ceiling; authors must cover the entire authorized ceiling to deny all amounts.

Consent and Acceptance have issued_at/expiry; require Intent issued_at ≤ Acceptance issued_at ≤ Consent issued_at < first executed action time, and action time inside all relevant intervals. Deadline does not extend expiry. Signed times remain claims requiring the pinned evidence/history, not independent trusted-clock proof. Invocation approvals are per-call, unique to invocation digest and issued before action. They are not reusable after plan/manifest/input changes.

## B2 — closed dependency vocabulary and trust

All dependency artifacts are SHA-256-addressed exact bytes. JSON dependencies use RFC8785 JCS UTF-8 without BOM; reject duplicate member names, non-I-JSON values and unsupported precision rather than normalize differently. Hash/ID rules are those in the profile; signed dependency types follow the same signing rule. A digest proves byte identity, not authority. A semantic consumer validates the artifact's closed object_type schema and the explicit role below. References used for policies must resolve to these types, not arbitrary prose/config. Blob data/input/output and application success criteria remain opaque evidence; they never grant authority.

| Reference / source | Required artifact type and interpretation |
|---|---|
| registry_snapshot_ref | RegistrySnapshot: exact ToolEntry refs, snapshot time, registrar signature. Entries match pinned list/version; no current-pointer lookup. |
| identity_profile_ref | IdentityProfile: exact trusted role key lists, delegation and key-event artifacts. Trust anchor is the principal key independently configured by the relying party; never accept a principal merely because the bundle nominates it. Principal signs Consent to the manifest fixing all other role keys. |
| confirmation_profile_ref | ConfirmationProfile: affirmative per invocation, restricted out-of-band; channel authority keys and ChannelReceipt refs; reuse forbidden. |
| evidence_profile_ref | EvidenceProfile: linear-bijection-stepbindings-v1, JCS-IJSON bytes and sha256-colon-lowerhex. Optional subjective evaluator keys/results cannot authorize actions. |
| budget_profile_ref | BudgetProfile: one deployment, pinned ledger authority, sequence of BudgetEvent refs. Protocol reserve-before-call-consume-or-release-v1; no cross-deployment concurrency. |
| relay_profile_ref | RelayProfile: mode none requires no fabricated chain/key; otherwise one pinned trust path, FinalityRule and signed RelayReceipt refs. |
| ToolEntry.behavior_ref | ToolBehavior: unique operation names, class labels and pure/external-state context mode, exact interface bytes. ToolEntry.interface_ref equals behavior.interface_bytes_ref. |
| DeploymentPolicy.extra_requirements_ref | RestrictionProfile: only none/affirmative/out_of_band extra confirmation and finite validity interval. Other restrictions use explicit deny_rules. Unknown requirement language unsupported. |
| custody access/export/challenge refs | CustodyAccessProfile: exact reader keys, complete export mode, retention/challenge/appeal endpoints. All three refs must identify this same artifact; retention covers both windows and agrees with CustodyProfile. |
| delegation/key_event refs | Delegation / KeyEvent objects as defined below. |
| approval.channel_evidence_ref | ConfirmationProfile artifact (not a receipt of the approval itself); must equal manifest's profile. Actual channel receipt is separately included by ConfirmationProfile and export. |
| relay.finality_rule_ref | FinalityRule: chain_id, relayer-asserted finality, minimum confirmations and maximum age. This is pinned-relayer trust, not native chain verification. |

Only pure Ed25519 per RFC8032 signing the 32-byte SHA-256 digest is supported. Signature value is 64-byte lowercase hex; actor identity is `ed25519:` + 32-byte public-key lowercase hex. key_ref resolves to exactly those 32 raw key bytes (media_type application/octet-stream), digest checked. No Ed25519ph, extra hashing, EIP-191, DID lookup or suite fallback. Signer actor binding is checked outside the excluded signature wrapper. Principal has no delegated approval in this bounded revision; actor identity must equal its independently trusted public key.

Root Agent either signs directly or supplies a non-cyclic ordered Delegation chain from the pinned agent root. Each Delegation is signed by issuer_key, parent at most one, first issuer_key equals issuer_root, next issuer_key equals prior subject_key, root stays constant, child limits strictly narrow, times fit parent and Acceptance. Acceptance.signer_key_ref resolves to final subject_key; all referenced chain bytes must be exported. KeyEvent is signed by its declared root (issuer=root), and covers that root/key's effective state. Missing fresh authoritative history prevents full verification. No event after compromise reactivates that compromised key in this revision; use a new key/Acceptance. Legacy compromised-proof timestamp rules remain unchanged. An agent root not in the principal-consented IdentityProfile cannot become trusted by signing its own entry.

ToolEntry signature is from a listed registrar, provider is explicit and behavior remains a claim subject to tool evidence. RegistrySnapshot registrar is also listed. DeploymentPolicy operator, Configuration provisioner and CustodyProfile custodian signatures must match their pinned role lists; each refers to the same identities selected by Consent. Extra requirements may only add restrictions; no state mutation of pinned artifacts. All finite intervals constrain actions. Missing artifacts/history are unavailable, invalid signatures are invalid, and truthful execution is separately unproved.

ChannelReceipt is signed by a pinned independent channel authority, naming principal, exact Invocation, mode, channel ID, time and **approval_signing_digest**. This is the digest already signed by InvocationApproval under the profile formula, not a reference cycle back into the manifest. ConfirmationProfile carries receipt refs, which creates a manifest/approval dependency cycle if the manifest attempted to include invocation-specific receipts before Acceptance. Therefore ConfirmationProfile.channel_receipt_refs MUST be empty in the pinned manifest; receipts are carried only in EvidenceBundle.exported_evidence_refs and matched by the invocation and approval digest. The empty list declares no historical receipts, not approval absence. Channel authority must differ from agent operational keys. Out-of-band channel evidence must be independently attributable under that selected authority; its claim is not proof of a physical human gesture. No live channel adapter is delivered.

BudgetEvent is signed by a listed ledger authority with exact deployment/Acceptance/Invocation/asset/network. Sequence starts at zero, previous_event_refs empty only for the first and otherwise exactly the immediately preceding event. History/export must be complete. reserve atomically checks available total budget and nonce/invocation uniqueness before action; consume finalizes reserved spending at no more than reservation, release cancels unused reservation, no second consume/release, no negative or cross-asset arithmetic. Reservation/consumption amounts must fit all authority ceilings and fee quote policy; total consumed plus outstanding reservation never exceeds the minimum applicable total ceiling. A signed sequence alone does not prove atomicity or absence of omitted history: ledger authority/state proof and supported runtime remain B4. Do not claim budget authorization without them.

For single-trust-path relay, RelayReceipt signer matches pinned relayer; chains and FinalityRule match, confirmation count meets threshold, observed_at is not future and age is no more than the minimum configured freshness limit. canonical_payload_ref resolves to exactly the JCS payload bytes verified and exported, not a substituted digest. Native finality/truth is not proven by this claim; heterogeneous relay paths unsupported. mode none must have no relay receipts and no cross-chain claim.

## B3 — exact step-binding bijection

EvidenceBundle.step_bindings is ordered and has exactly the same length as aggregate.steps, invocation_refs and Plan.ordered_actions. step_index and Invocation.plan_index equal the array index 0..N−1. invocation_refs[i] equals binding[i].invocation_ref; Invocation.acceptance_ref and bundle Acceptance/Intent/manifest agree. No repeated Invocation ID, skipped/reordered/extra step or reused approval. Same tool can occur more than once only as distinct indexed Invocations with distinct nonce.

For every i:

1. Resolve complete aggregate artifact, verify its existing signature using the pinned evidence/identity rules; do not slice. For this profile intent_id equals referenced Intent.id, mandate_id equals Acceptance.id, and revealed plan is the complete Plan object. Acceptance.plan_ref matches Plan.id. Initial chained prev_hash equals SHA-256 of exact JCS complete Plan bytes, represented sha256:lowerhex; legacy formula remains untouched. In chained mode require links on all steps, recompute original step_hash formula excluding prev_hash; in flat mode all prev_hash fields are absent. This revision does not accept mixed partial chains.
2. Invocation matches plan_index template, tool_id/version and operation/resource/limits, and exact input digest. Resolved ToolEntry must be present in pinned manifest and registry snapshot; DeploymentPolicy must reference that baseline. aggregate step.tool_id equals ToolEntry.tool_id. Full version and invocation identity live in binding, not retrofitted into legacy step fields.
3. input_ref and output_ref resolve to canonical JCS JSON bytes (media_type application/json). input_ref equals Invocation.input_ref and Plan template input_ref. Step input_hash/output_hash equal their sha256:lowerhex digests. A full delivery claim's output hash is that returned object, not its embedded evidence hash. step_digest equals SHA-256(JCS(complete step including prev_hash when present)); this binding digest is distinct from the unchanged legacy step_hash used for linkage.
4. For a pure operation there must be zero binding context refs, no step context_hash, and no hidden config/state. External-state mode requires exactly one ContextManifest and step.context_hash equal SHA-256(JCS(complete resolved ContextManifest including its id)). Its pre-state/procedure/config/provenance refs must cover the selected behavior's actual dependencies before the call; missing evidence cannot be patched with an empty/zero hash. Multiple Invocations may share identical immutable context bytes only if each call's provenance establishes that same pre-state/procedure/config at its execution time. Context observed_at must precede or equal step timestamp. A post-state digest is output evidence, never pre-state.
5. bundle.context_refs is the unique set of all binding context refs, no orphan/extra contexts. Each input/output/context/call claim has exported bytes and attributable provenance; Invocation issued_at and every approval/validity interval fit step.timestamp. Metadata times alone do not prove real ordering. Missing trusted time evidence prevents a full temporal claim.

EvidenceBundle itself is content-addressed, not inherently signed: verify aggregate signature plus every principal Consent, Agent Acceptance, Invocation approval, manifest dependencies and step correspondence. A substituted outer bundle cannot pass merely because its id is internally valid. Deletion of required sidecar bytes may preserve history while making semantic/replay verification unavailable. Semantic success, runtime honesty and physical outcomes remain separate.

## Synchronized acceptance conditions

Document/structure checks: 28 closed object alternatives, schema refs/meta-schema, mandatory one Consent and required step_bindings, typed dependencies and draft-revision compatibility notice; legacy formulas/code blocks and license/contributor bytes unchanged.

Future semantic conformance cases (not executed here): missing/changed Consent; same principal ID with different key; unknown suite; wrong role signer; delegation widening/cycle/expired key; policy widening/unknown language; circular approval receipt; false byte digest; duplicate/skip/reordered step; swapped contexts for same tool; orphan context; absent output; flat/chained mode mismatch; plan substitution; future receipt; stale key history; unsupported budget authority; omitted reservation events. Shape pass is not authorization, atomicity or outcome verification.

B1–B3 are closed as bounded revision-2 specification choices. B4 ledger/runtime atomicity and B5 verifier/cryptographic qualification remain blocked, as do declared unsupported parallel, heterogeneous relayers and cross-deployment replay guarantees. No implementation or experiment is supplied. #4–#8 remain open. Original options, contributors and licenses remain historical records, not evidence of their agreement with these decisions.
